سند فنی جامع و مستندات تصمیم‌گیری معماری (ADR)

این مستند، کالبدشکافی فنی کامل پروژه «انبار» (Anbar B2B Warehouse & Smart Invoicing) را ارائه می‌دهد. برای هر انتخاب فنی، منطق پیاده‌سازی، آلترناتیوهای رقیب، نقاط قوت و ضعف و دلیل انتخاب آن به صورت مو به مو تبیین شده است.

۱ نمای کلی سیستم و دیاگرام جریان داده (System Architecture)

Next.js 16 + Neon PostgreSQL

سامانه «انبار» یک مونو-ریپوی ماژولار است که بر پایه معماری Serverless First بنا شده است. هدف کلیدی این معماری: «نگهداری صفر، سرعت بی‌نظیر برای کاربران موبایل و یکپارچگی اتمیک داده‌های موجودی و مالی» بدون تحمیل هزینه‌های سنگین سرور اختصاصی است.

۲ فریم‌ورک کلان: چرا Next.js 16 (App Router + Turbopack)؟

Framework Decision

برای توسعه سامانه انبارداری، ساختار یکپارچه Full-stack با استفاده از Next.js 16 و هسته Turbopack انتخاب شد.

انتخاب شده: Next.js 16 (App Router)

مزایای کلیدی

  • تایپ‌سیفتی سرتاسری (End-to-End TypeScript): اشتراک مدل‌های اعتبارسنجی Zod و تایپ‌های Prisma بین فرانت‌اند و بک‌اند بدون کوچکترین ناهماهنگی قراردادها (Contract Drift).
  • هسته کامپایل فوق‌سریع Turbopack: بیلد و Hot Reload در کسری از ثانیه در مقایسه با وب‌پک‌های سنتی.
  • مسیریابی مدرن App Router: استفاده از Layout‌های تو در تو، استریمینگ با React Suspense و متدهای بهینه سرور.
  • زیرو-اوپس (Zero-Ops): استقرار با یک کلیک بر روی Vercel بدون نیاز به کانفیگ Nginx، داکر یا سرور لینوکس.
آلترناتیو ۱: بک‌اند مجزا با NestJS / Express + فرانت‌اند SPA (Vite React)

چرا انتخاب نشد؟

  • دو برابر شدن سربار نگهداری: نیاز به دو ریپازیتوری مجزا یا مدیریت پکیج‌های مشترک (Monorepo Turborepo)، دو خط پایپلاین CI/CD مجزا، و دو سرور مختلف.
  • سربار شبکه و CORS: ایجاد درخواست‌های اضافی OPTIONS پیش‌پرواز (Preflight) که سرعت باز شدن کاتالوگ موبایل برای مشتری را تا ۳۰۰ میلی‌ثانیه کند می‌کرد.
  • تکرار مدل‌ها: الزام به ساخت DTO در نست‌جی‌اس و تعریف مجدد اینترفیس‌ها در فرانت‌اند.
آلترناتیو ۲: Remix / React Router v7

چرا انتخاب نشد؟

  • اکوسیستم ابزارها و لایبرری‌های جانبی (نظیر افزونه‌های Vercel، پکیج‌های اکسل و پرینت) برای Next.js بسیار بالغ‌تر و پایدارتر است.
  • مستندات و تسلط مهندسی تیم بر اکوسیستم استاندارد Next.js بیشتر بود و ریسک‌های فاز استقرار را به صفر می‌رساند.

۳ پایگاه داده: چرا Neon Serverless PostgreSQL؟

داده‌های انبارداری و پیش‌فاکتورها به دلیل حساسیت‌های مالی ماده ۱۶۹ و موجودی کالاها، نیازمند قوانین سخت‌گیرانه ACID و تراکنش‌های تضمین‌شده هستند.

الگوی اتصال دوگانه (Dual-Connection Pattern): سامانه از دو رشته اتصال در .env بهره می‌برد:
  1. DATABASE_URL: متصل به پورت پولینگ PgBouncer (پورت ۶۵۴۳) جهت هندل کردن هزاران درخواست همزمان بدون مصرف ظرفیت کانکشن‌های فیزیکی دیتابیس.
  2. DIRECT_URL: اتصال مستقیم به سرور اصلی پستگرس (پورت ۵۴۳۲) مختص مایگریشن‌های ساختاری Prisma و دستورات DDL که توسط پولر مسدود می‌شوند.

۴ لایه ORM و دسترسی به داده: معماری Prisma 7 و Driver Adapter

Prisma 7 + @prisma/adapter-pg

این پروژه از نسل جدید Prisma 7+ بهره می‌برد که ساختار معماری آن نسبت به نسخه‌های سنتی کاملاً بازطراحی شده است.

معماری نوین Prisma 7

تغییر بنیادین مدیریت کانکشن‌ها

در پریزما ۷، ویژگی قدیمی url = env(...) داخل فایل schema.prisma منسوخ شده و خطای P1012 پرتاب می‌کند. در این پروژه، مدیریت کانکشن‌ها به فایل رسمی prisma.config.ts و درایور آداپتور @prisma/adapter-pg منتقل شده است.

src/lib/db.ts
import { Pool } from 'pg';
import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from '@prisma/client';

const pool = new Pool({
  connectionString: process.env.DIRECT_URL || process.env.DATABASE_URL,
});
const adapter = new PrismaPg(pool);
export const db = new PrismaClient({ adapter });

چرا Drizzle انتخاب نشد؟

  • سرعت توسعه (Developer Velocity): سینتکس شمای پریزما بسیار خواناتر است و به صورت خودکار مدل‌های دیتابیس، ایندکس‌ها، و ارتباطات ۱ به چند و چند به چند را در یک فایل منفرد مدیریت می‌کند.
  • موتور یکپارچه مایگریشن (Prisma Migrate): پریزما تاریخچه مایگریشن‌ها را به صورت فایل‌های امن SQL خروجی می‌دهد و از تداخل اسکیماها در تیم‌های چند نفره جلوگیری می‌کند.
  • دریزل با وجود وزن کمتر، برای پروژه‌های تجاری سنگین با قوانین مالیاتی ماده ۱۶۹ نیازمند نوشتن دستی مایگریشن‌ها و تایپ‌های پرتیپو بود.

۵ سیستم مجوزهای اتمیک مبتنی بر بیت‌ماسک (Bitmask Authorization)

Security & Performance

یکی از نوآوری‌های مهم معماری انبار، استفاده از مدل سطوح دسترسی بیتی (Bitmask RBAC) به جای سیستم‌های جدول‌محور سنتی است.

نقش و عملیات سیستم بیت ریاضی مقدار ده‌دهی (Mask) توضیحات و مجوزهای عملیاتی
VIEW (مشاهده عمومی) 1 << 0 1 مشاهده لیست کالاها، دسته‌بندی‌ها و موجودی انبار
CREATE_EDIT (تعریف و ویرایش) 1 << 1 2 افزودن کالای جدید، ویرایش قیمت‌ها و مشخصات فنی
DELETE (حذف اقلام) 1 << 2 4 حذف رکورد کالاها و پیش‌فاکتورها
STOCK_MOVE (انبارداری و ورود/خروج) 1 << 3 8 ثبت حواله ورود، خروج، انبارگردانی و کسری
MANAGE_LINKS (مدیریت کاتالوگ‌ها) 1 << 4 16 ساخت و انقضای لینک‌های اختصاصی خریداران
SETTINGS (تنظیمات سربرگ و مالیات) 1 << 5 32 تغییر درصد مالیات ماده ۱۶۹، شبا و مشخصات شرکت
EXPORT_IMPORT (اکسل و پشتیبان) 1 << 7 128 درون‌ریزی و استخراج فایل اکسل موجودی کالا
SUPER_ADMIN (مدیر ارشد انبار) ALL_BITS 255 دسترسی نامحدود به کلیه بخش‌ها و تعاریف مدیریتی
چرا بیت‌ماسک؟ (The Rationale)
  • سرعت محاسباتی در حد نانوثانیه: ارزیابی دسترسی صرفاً با یک عملگر بیتی پردازنده انجام می‌شود: (userRole & requiredMask) === requiredMask.
  • حذف ۴ جدول رابطه‌ای دیتابیس: در سیستم سنتی به ۴ جدول roles، permissions، user_roles و role_permissions با چندین دستور سنگین SQL JOIN نیاز بود. در بیت‌ماسک، کل دسترسی کاربر فقط در یک فیلد ساده SMALLINT ذخیره می‌شود!
  • امکان ترکیب نامحدود مجوزها: مثلاً نقش «انباردار ارشد» با مجموع دسترسی‌ها: 1 + 2 + 8 + 128 = 139 در کسری از ثانیه ساخته می‌شود.
آلترناتیوها: Clerk یا Auth0 یا پکیج Casbin
  • عدم وابستگی به سرویس‌های خارجی (No Vendor Lock-in): سرویس‌های ابری مانند کلرک یا آوث۰ علاوه بر تحریم بودن برای کاربران ایرانی، در صورت قطع اینترنت بین‌الملل سیستم انبارداری شرکت را فلج می‌کنند.
  • هزینه صفر: مدیریت احراز هویت داخلی هیچ هزینه ماهانه یا محدودیت تعداد کاربر فعالی به سیستم تحمیل نمی‌کند.

۶ مدیریت سشن در فرانت‌اند و معماری احراز هویت (Frontend Session Lifecycle)

AuthContext + HttpOnly

مدیریت نشست‌های کاربری (Session Management) در فرانت‌اند انبار طبق رویکرد «امنیت لایه‌ای بدون ریدیس (Layered Zero-Trust Architecture)» پیاده شده است. هیچ توکنی در localStorage ذخیره نمی‌شود و فرانت‌اند از طریق کوکی‌های امن با سرور همگام است.

لایه ۱: کوکی HttpOnly امن

مصونیت ۱۰۰٪ در برابر حملات XSS

توکن JWT در کوکی anbar_session با فلگ‌های httpOnly: true، SameSite: 'lax' و Secure ذخیره می‌شود. کد جاوااسکریپت فرانت‌اند به این کوکی دسترسی خواندن ندارد، بنابراین اسکریپت‌های مخرب تحت هیچ شرایطی امکان سرقت سشن را ندارند.

لایه ۲: پراکسی رهگیر (src/proxy.ts)

گارد سرورلس پیش از رندر صفحات

پیش از رندر هر صفحه در Next.js، فایل proxy.ts کوکی ورودی را رهگیری و با کلید محرمانه ۵۱۲ بیتی با کتابخانه jose اعتبارسنجی می‌کند. کاربر احرازنشده به مسیرهای حفاظت‌شده مانند /admin در کسری از میلی‌ثانیه به /login ریدایرکت می‌شود.

لایه ۳: کانتکست React (AuthContext)

مدیریت سشن در حافظه (In-Memory State)

هوک useAuth() مشخصات کاربر (id, email, role) را در وضعیت داخلی React ذخیره نموده و توابع ارزیابی سریع بیت‌ماسک (can, canAny, canAll) را به تمامی کامپوننت‌های پنل مدیریت تزریق می‌کند.

چرخه حیات سشن در فرانت‌اند (Frontend Session Step-by-Step):
  1. بارگذاری اولیه صفحه (Bootstrapping): در هنگام مانت شدن کامپوننت ریشه، هوک useEffect متد refreshUser() را فراخوانی می‌کند.
  2. احراز هویت بدون ارسال توکن دستی (Automatic Transport): تابع refreshUser یک درخواست GET /api/auth/me ارسال می‌کند. مرورگر کوکی HttpOnly را به شکل خودکار در هدر ضمیمه می‌نماید.
  3. تزریق استیت در حافظه (Hydration): پس از تایید سرور، مشخصات کاربر و نقش عددی بیت‌ماسک بارگذاری شده و فلگ isLoading به false تغییر می‌یابد.
  4. کنترل دسترسی المان‌ها (<PermissionGate>): کامپوننت‌های واسط کاربری با بهره‌گیری از بیت‌ماسک‌ها و گیت اختصاصی <PermissionGate permission={Permission.STOCK_MOVE}> دکمه‌ها و فرم‌ها را مشروط می‌سازند.
  5. خروج امن (Sign-Out): متد logout() درخواست POST /api/auth/logout را صادر کرده، کوکی در سمت سرور با maxAge: 0 باطل می‌شود، استیت فرانت‌اند پاک شده و کاربر به /login هدایت می‌گردد.
معیار ارزیابی امنیت و فرانت‌اند رویکرد سامانه انبار (HttpOnly Cookie + React State) رویکرد سنتی (LocalStorage Bearer Token)
مقاومت در برابر سرقت با XSS ✓ ۱۰۰٪ مصون: جاوااسکریپت امکان خواندن کوکی HttpOnly را ندارد. ! آسیب‌پذیر بحرانی: هر اسکریپت آلوده یا پکیج npm مخرب توکن را سرقت می‌کند.
سربار کدنویسی در درخواست‌های API ✓ صفر: مرورگر خودبه‌خود کوکی را در تمام فراخوانی‌های fetch الصاق می‌نماید. ! بالا: الزام به ساخت Interceptor در Axios یا الحاق دستی هدر Bearer در هر کوئری.
محافظت در برابر CSRF ✓ تضمین‌شده: با فلگ SameSite: 'lax' مرورگر اجازه ارسال کراس-سایت را نمی‌دهد. در برابر CSRF امن است اما در برابر XSS کلاً بی‌دفاع است.
سربار حجم باندل جاوااسکریپت ✓ کمتر از ۲ کیلوبایت: کد کاملاً بومی بر پایه هوک‌های React. ! بالای ۱۰۰ کیلوبایت: پکیج‌های سنگین SDK نظیر Auth.js یا Firebase.

۷ کنترل همزمانی و کسر اتمیک موجودی انبار (Atomic Stock Concurrency)

Inventory Engine

یکی از بحرانی‌ترین مخاطرات در انبارهای بزرگ، تداخل همزمانی سفارشات (Race Conditions) است؛ زمانی که موجودی یک شیر صنعتی ۵ عدد است و دو خریدار به طور همزمان هرکدام سفارش ۴ عددی ثبت می‌کنند.

پیاده‌سازی ما: عملیات شرطی اتمیک دیتابیس (Atomic Conditional Updates)

به جای خواندن موجودی و سپس کاهش دادن آن با دو کوئری جداگانه، دستور کاهش انبار به صورت اتمیک و در یک کوئری تراکنشی اجرا می‌شود:

Atomic Decrement Transaction
await db.$transaction(async (tx) => {
  const updated = await tx.product.updateMany({
    where: {
      id: productId,
      stockQuantity: { gte: requestedQty } // گارد شرطی اتمیک
    },
    data: {
      stockQuantity: { decrement: requestedQty }
    }
  });

  if (updated.count === 0) {
    throw new Error('کسری موجودی انبار توسط سفارش همزمان!');
  }
});
آلترناتیوها: قفل ریدیس (Distributed Locks / Redlock) یا Pessimistic Lock
  • چرا Redis Redlock انتخاب نشد؟ نیاز به استقرار یک کلاستر مجزای Redis داشت که اصل «نگهداری صفر» سیستم را نقض می‌کرد و در صورت قطعی شبکه باعث بن‌بست (Deadlock) می‌شد.
  • دفترکل انبار (Audit Trail): کلیه ورود و خروج‌ها علاوه بر جدول کالا، در جدول تاریخی StockMovement به همراه علت (مانند تبدیل به پیش‌فاکتور REQ-102) و شناسه کاربر ثبت می‌گردد تا تاریخچه حسابرسی دست‌نخورده باقی بماند.

۸ منطق کالاهای سفارشی و ساخت بر اساس تقاضا (Made-to-Order)

B2B Custom Logic

در بازارهای صنعتی، بسیاری از اتصالات، مخازن یا لوله‌ها دپوی آماده در قفسه انبار ندارند بلکه بر اساس متراژ و نقشه خریدار تراشکاری یا وارد می‌شوند.

ویژگی isCustom: true و زمان تخمینی تحویل:
  • برای اقلام سفارشی، محدودیت سقف موجودی انبار غیرفعال می‌شود تا مانع ثبت سبدهای خریدار نشود.
  • در کاتالوگ آنلاین مشتریان، برچسب زرد/آبی «سفارشی / ساخت بر اساس تقاضا» همراه با تخمین زمان ساخت (مثال: «۳ تا ۵ روز کاری») نمایش می‌یابد.
  • در صدور فاکتور و کسر موجودی، این اقلام انبار فیزیکی را دچار منفی شدن فرضی نمی‌کنند اما ردیف مالی آنها در پیش‌فاکتور رسمی درج می‌گردد.

۹ کاتالوگ مشتریان و اشتراک‌گذاری بدون اصطکاک (Frictionless B2B Portal)

Client Experience

بزرگ‌ترین گلوگاه سامانه‌های سنتی این بود که مشتری برای دیدن قیمت باید اپلیکیشن نصب می‌کرد، ایمیل تایید می‌کرد یا رمز عبور به خاطر می‌سپرد؛ رفتاری که بازرگانان بازار سنتی فوراً آن را ترک می‌کردند!

پیاده‌سازی ما: توکن‌های یکتای وب (/c/[token])
  • ورود تک‌کلیکی: مشتری با لمس لینک در واتساپ یا تلگرام بدون هیچ لاگینی کاتالوگ سفارشی خود را می‌بیند.
  • تخفیف‌های اختصاصی در لینک: توکن کاتالوگ تعیین می‌کند کدام دسته کالاها یا چه درصد تخفیفی برای این خریدار خاص لحاظ گردد.
  • انقضا و نظارت: مدیر می‌تواند برای هر پیوند زمان انقضا تعیین کند یا هر زمان خواست آن را با یک کلیک غیرفعال نماید.
آلترناتیو سنتی: لاگین با پیامک OTP یا پورتال ثبت‌نام
  • هزینه سنگین پیامک: سامانه‌های پیامکی در ایران نیازمند خطوط خدماتی، تایید مدارک شرکتی و هزینه به ازای هر پیام هستند.
  • افت شدید نرخ تبدیل (Drop-off Rate): تجربه نشان داده بیش از ۶۰٪ خریداران سازمانی در مواجهه با صفحه ثبت‌نام اولیه، فرآیند استعلام را نیمه‌کاره رها می‌کنند.

۱۰ محاسبات مالی، گردکردن امن و انطباق با ماده ۱۶۹ م.م.

Financial Engine

صورتحساب‌های تولیدشده در سامانه با ضوابط سامانه مودیان و ماده ۱۶۹ قانون مالیات‌های مستقیم کاملاً منطبق است.

  • جلوگیری از باگ‌های Floating-Point در جاوااسکریپت: در جاوااسکریپت عباراتی مثل 0.1 + 0.2 حاصل 0.30000000000000004 می‌دهند که در مبالغ میلیاردی تومانی فاجعه‌آفرین است. ماژول محاسباتی پروژه از متدهای امن safeCurrencyRound بهره می‌برد.
  • سربرگ رسمی استاندارد: چاپ خودکار نام بازرگانی، شناسه ملی (National ID)، کد اقتصادی، کد پستی ۱۰ رقمی و شماره شبای بانکی در بالای نسخه چاپی پیش‌فاکتور.
  • چاپ استاندارد A4 با CSS چاپی: استفاده از استایل‌های اختصاصی @media print تا بدون نیاز به تولید عکس‌های سنگین، مستقیماً از داخل هر مرورگری با کلید Ctrl+P خروجی دقیق PDF صفحه پیش‌فاکتور با رزولوشن ۳۰۰ DPI پرینت شود.

۱۱ مدیریت وضعیت سرور: TanStack Query v5 (React Query)

Frontend State

به جای ذخیره داده‌های سرور در وضعیت محلی ریداکس، کل چرخه حیات درخواست‌های موجودی و سفارش‌ها به TanStack Query v5 سپرده شده است.

مزایای انتخاب React Query v5
  • کشینگ هوشمند (Smart Cache Invalidation): بلافاصله پس از ثبت یک سفارش جدید یا تغییر موجودی کالا، کوئری‌های مرتبط با کلید ['products'] باطل شده و داده‌های جدید به شکل پس‌زمینه بروزرسانی می‌شوند.
  • بروزرسانی خوش‌بینانه (Optimistic Updates): شمارنده سبد خرید بدون معطلی سرور تغییر می‌کند و تجربه نرم‌افزار نیتیو موبایل را به خریدار القا می‌نماید.
  • مدیریت خودکار وضعیت‌های بارگذاری و خطا: متغیرهای isLoading و isError به طور بومی در دسترس کامپوننت‌ها قرار دارند.
آلترناتیوها: Redux Toolkit یا Zustand یا useEffect سنتی
  • ریداکس برای نگهداری داده‌های سروری (Server State) کدهای تکراری طاقت‌فرسایی تولید می‌کند و مدیریت کش، زمان انقضا و بازخوانی هنگام فوکوس پنجره را ندارد.
  • استفاده از useEffect خام باعث باگ‌های متعدد رندر مجدد (Re-render) و مسابقه داده‌ها (Race conditions) در کامپوننت‌ها می‌شد.

۱۲ مجازی‌سازی لیست‌های سنگین کالاها (@tanstack/react-virtual)

Performance Optimization

زمانی که کاتالوگ انبار حاوی ۳۰۰۰ تا ۱۰,۰۰۰ قلم کالا باشد، رندر کردن تمامی تگ‌های HTML در DOM گوشی خریدار باعث افت فریم شدید و بسته شدن خودکار مرورگر گوشی (Crash) می‌شود.

چرا مجازی‌سازی با useWindowVirtualizer؟
  • در هر لحظه صرفاً اقلامی که داخل دید کادر صفحه موبایل قرار دارند (حدود ۱۰ الی ۱۵ المان) در حافظه رندر می‌شوند.
  • با اسکرول سریع مشتری، المان‌های خارج شده از کادر از DOM پاک شده و المان‌های جدید بازتولید می‌شوند.
  • نتیجه: مصرف حافظه RAM روی مرورگرهای موبایل تا ۹۰٪ کاهش یافته و اسکرول ۶۰ فریم بر ثانیه تضمین می‌گردد.

۱۳ سیستم طراحی، تم‌های روز/شب و قواعد راست‌به‌چپ (RTL & BiDi)

UI/UX Architecture

طراحی ظاهری سامانه طبق بالاترین استانداردهای بصری و تعاملی با Tailwind CSS پیاده شده است:

  • موتور تم تیره و روشن واقعی: تغییر بلادرنگ تم از طریق متغیرهای معنایی CSS و ذخیره انتخاب کاربر در localStorage.
  • حل ریشه‌ای باگ‌های چینش نمادها در RTL (BiDi Unicode): در متن‌های فارسی، نمایش اعداد دارای مثبت/منفی یا درصد (مثل +2 یا 50% یا شماره‌های فنی SKU) دچار جابجایی کاراکتر می‌شوند. سامانه با تزریق کاراکتر مخفی استاندارد \u200E (Left-to-Right Mark) و کانتینرهای با دایرکشن صریح dir="ltr" این نقص را به کلی رفع کرده است.
  • سامانه اعلانات و تاییدیه اختصاصی (notify): استفاده از window.confirm و window.alert مسدود شده و با پاپ‌آپ‌های متحرک، غیرمسدودکننده و هماهنگ با تم تیره جایگزین شده است.

۱۴ استراتژی تضمین کیفیت و تست با Vitest

QA & Testing Suite

تمام منطق‌های محاسباتی، احراز هویت، بیت‌ماسک‌ها و لایه اعتبارسنجی با ۳۴ تست واحد (Unit Tests) با فریم‌ورک Vitest پوشش داده شده‌اند.

چرا Vitest به جای Jest؟
  • سرعت خیره‌کننده: اجرای تمام ۳۴ تست در کمتر از ۷۰۰ میلی‌ثانیه به دلیل ساختار Native ESM و ترد‌های سبک Vite.
  • سازگاری کامل با TypeScript مدرن: بدون نیاز به پیکربندی‌های سنگین و دردسرساز ts-jest یا کانفیگ‌های ناسازگار با اکمااسکریپت.
  • حجم ناچیز دپندنسی‌ها: عدم تحمیل ده‌ها مگابایت کتابخانه‌های جانبی عهد عتیق وب‌پک به پروژه.
حوزه‌های تحت پوشش تست‌ها
  • تست دسترسی‌های بیت‌ماسک: تضمین صحت ترکیب و تجزیه دسترسی‌ها برای تمام ۲۵۵ سطح مجوز.
  • تست محاسبات پیش‌فاکتور: اعتبارسنجی جمع اقلام، مالیات بر ارزش افزوده و تخفیف‌ها.
  • تست امنیت احراز هویت و ریت‌لیمیت: تست مسدودسازی حملات Brute-force در درخواست‌های ورود.

۱۵ ماتریس جامع مقایسه فنی و دلایل ترجیح (Master Decisions Matrix)

Executive Summary

جدول زیر خلاصه مقایسه‌ای تصمیمات مهندسی در برابر مهم‌ترین آلترناتیوهای صنعت نرم‌افزار است:

بخش فنی فناوری برگزیده در انبار مهم‌ترین آلترناتیو علت ترجیح فناوری برگزیده چه زمانی بازنگری شود؟
معماری کلان Next.js 16 App Router NestJS + React SPA یکپارچگی تایپ‌ها، سرعت استقرار، صفر بودن سربار DevOps در صورت افزایش تعداد توسعه‌دهندگان بک‌اند به بیش از ۱۰ نفر
پایگاه داده Neon Serverless Postgres Docker Postgres on VPS مقیاس‌پذیری خودکار، قابلیت برنچینگ، نگهداری صفر در صورت لزوم قرارگیری سرور داخل دیتاسنتر محلی خاص به دلایل رگولاتوری
لایه ORM Prisma 7 + Adapter-PG Drizzle ORM مایگریشن‌های اسکیما-محور پایدار، تایپ‌های سرتاسری و اکوسیستم بالغ اگر نیاز به پرفورمنس میکرو-ثانیه‌ای در کوئری‌های تحلیلی عظیم باشد
مدل دسترسی Bitmask Integer (0..255) Multi-table RBAC Join صفر شدن کوئری‌های SQL JOIN، سرعت نانوثانیه، صرفه‌جویی در فضای دیتابیس در صورت نیاز به بیش از ۳۲ مجوز مستقل سازمانی
احراز هویت JWT در HttpOnly Cookie Server Sessions در Redis بی‌حالت (Stateless) بودن در محیط‌های سرورلس بدون نیاز به کلاستر ریدیس اگر نیاز به ابطال بلادرنگ سشن‌ها از پنل مرکزی فوراً وجود داشته باشد
کنترل همزمانی انبار Atomic Decrement Condition Redis Redlock انزوای اتمیک سطح پایگاه داده بدون وابستگی به زیرساخت جانبی اگر تراکنش‌های همزمان در ثانیه به بالای ۵۰۰۰ سفارش برسد
پورتال مشتریان لینک اختصاصی وب (/c/[token]) لاگین اجباری با OTP پیامک حذف هزینه پیامک، بالا بردن شدید نرخ ثبت سفارش خریداران اگر نیاز به احراز هویت حقوقی پیش از مشاهده قیمت‌ها الزامی شود
وضعیت کلاینت TanStack Query v5 Redux Toolkit مدیریت خودکار کش، باطل‌سازی کلیدها و بروزرسانی خوش‌بینانه اگر نیاز به وضعیت‌های شدیداً پیچیده فرانت‌اندی بدون منشا سرور باشد
فریم‌ورک تست Vitest Jest اجرای ۷۰۰ میلی‌ثانیه‌ای، هماهنگی کامل با ESM مدرن، بیلد فوق‌سریع هیچ دلیلی برای بازگشت به Jest وجود ندارد
نتیجه‌گیری راهبردی (Architectural Conclusion): طراحی مهندسی سامانه انبار به گونه‌ای استوار است که هم برای یک انبار تجاری متوسط با سرعت اجرا شود و هم تا مقیاس صدها هزار رکورد کالا و پیش‌فاکتورهای متعدد همزمان، بدون نیاز به ری‌فکتورهای اساسی یا هزینه‌های گزاف ابری، با نهایت پایداری پاسخگوی عملیات بازرگانی باشد.
